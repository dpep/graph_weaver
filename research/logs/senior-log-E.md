23:38:00 — LIVE Hasura (PokeAPI, https://beta.pokeapi.co/graphql/v1beta) probes via curl (hit its rate limit twice, ~1min total backoff, logged as dead-end-adjacent but resolved by retry, not counted as a real dead end). Four raw responses captured, then fed through GraphWeaver::GraphQLError.from_h(...).input_errors in spec/graphql/live_hasura_spec.rb (4 examples, green):

1. wrong-typed `where:` value (`{id: {_eq: "not-an-int"}}` against an Int column) -- Hasura's own bool_exp layer accepts the literal (it's a generic comparison exp), the rejection happens one layer down at Postgres: `{"message":"invalid input syntax for type integer: \"not-an-int\"","extensions":{"path":"$","code":"data-exception"}}`. `data-exception` is NOT one of the two codes graph_weaver reads (`validation-failed`/`parse-failed`), so `#input_errors` is `[]` -- and even `path` ("$") wouldn't have named an argument if it tried. Not a graph_weaver bug (matches the documented "anything else says nothing" fallback), but a real, easy-to-hit gap: the single most common Hasura input mistake -- a string where the column wants a number -- is INVISIBLE to `#input_errors` for a filter column whose comparison type isn't itself scalar-typed as Int in the schema (many are typed loosely as the comparison-exp "any"). A team building a form on `#input_errors` alone will silently miss this class of rejection and must fall back to `#errors`.
2. unknown column in `where:` -- `code":"validation-failed"`, path `$.selectionSet.pokemon_v2_pokemon.args.where.nonexistent_column` -> kind `:unknown`, `#path` = `["where", "nonexistent_column"]`, lands on the argument correctly.
3. bad enum in `order_by:` -- kind `:not_a_member`, `#path` = `["order_by", 0, "name"]` (the `[0]` bracket segment parsed correctly into a real list index), `details[:members]` is the full 6-value array. Lands on the argument correctly, index and all.
4. `limit:` a String instead of Int -- kind `:refused` (Hasura's "expected a non-negative 32-bit integer... but found a string" is the SAME sentence it uses for a negative limit, so graph_weaver correctly refuses to guess out_of_range vs type_mismatch, exactly as docs/errors.md states) but `#path` = `["limit"]` DOES land on the argument even though the kind is coarse.

Net: 3 of 4 live Hasura shapes work exactly as documented, arguments correctly named including a nested list index. The one gap (data-exception / Postgres-level type errors) is consistent with the documented "anything else" fallback but is worth flagging because it is the most common wrong-typed-filter-value case in practice, not an edge case.
