**Finding — HIGH — a subgraph that imports `@key` under a per-directive alias (`import: [{name: "@key", as: "@primaryKey"}]`, spec-legal syntax) crashes loading the raw subgraph SDL, with a message that blames the user for something they didn't do wrong.**
Repro: `tmp/h/link_alias.graphql` —
```graphql
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.9", import: [{name: "@key", as: "@primaryKey"}])
type Widget @primaryKey(fields: "id") { id: ID! name: String! }
```
`GraphWeaver::SchemaLoader.load(sdl)` raises:
```
GraphWeaver::Error: couldn't build a schema from a federation subgraph SDL — a directive it applies
may be outside the subgraph spec; declare that one in the file (NoMethodError: undefined method
'get_argument' for an instance of GraphQL::Schema::LateBoundType)
```
Root cause (`lib/graph_weaver/schema_loader.rb`): `subgraph_namespace(sdl)` (line 265) only extracts a *whole-spec* rename (`@link(..., as: "fed")` → every directive `fed__key`) via a regex against the federation `@link`'s own `as:` argument. It has no notion of a *per-directive* `import:` alias (`{name: "@key", as: "@primaryKey"}}`) — that machinery (`link_namespaces`/`imports`, lines 370-430) exists and is exactly what's needed, but it's wired up only for supergraph `@inaccessible` stripping, not for `add_subgraph_definitions`/`entity_names` on the subgraph-SDL path. This is the one place in the codebase where `@link`'s `import:`-with-`as:` is read for the supergraph path but not the subgraph path, and it's a real gap: an org that renames `@key` to avoid colliding with an existing scalar/directive named `key` in their own schema (a real reason to alias it) can publish a perfectly valid subgraph that graph_weaver can't load standalone (`_entities` typing, `Representations` builders) even though the very same subgraph composes and routes fine once it's part of a supergraph. Additive fix: reuse `link_namespaces`/`imports` inside `subgraph_namespace`/`add_subgraph_definitions`/`entity_names` instead of only checking the whole-spec `as:`.

11:05 - **A `@key` field set with a list inside DOES compose** (retracted my earlier wrong guess — see 10:45): `Order @key(fields: "id lineItems { sku }")` where `lineItems: [LineItem!]!` composes cleanly with `@apollo/composition` (no error). So this is a live, reachable shape, and:

**Finding — HIGH — a `@key` selecting into a list field builds a structurally-wrong representation, and refuses the one shape that would actually be correct.** Generated `Representations.order` for `Order @key(fields: "id lineItems { sku }")`:
```ruby
sig { params(id: String, line_items: T::Hash[T.untyped, T.untyped]).returns(...).checked(:never) }
def self.order(id:, line_items:)
  GraphWeaver::Representation.build("Order", {
    "id" => ...,
    "lineItems" => line_items,
  }, [["id", "lineItems.sku"]])
end
```
`lineItems: [LineItem!]!` is a **list**, but codegen (`lib/graph_weaver/codegen.rb#key_params`, the `else` branch at line 640-646: "a nested key set — or an enum/composite one — passes through as an open hash") only distinguishes SCALAR from everything else — it never checks `field.type.list?`, so a list-of-objects key field is typed identically to a plain nested object (`T::Hash[T.untyped, T.untyped]`). Calling it with the semantically correct value — an **array** of per-item hashes, `line_items: [{"sku"=>"a"},{"sku"=>"b"}]` — is refused:
```
GraphWeaver::InputError: Order representation is missing @key "lineItems.sku"
```
verbatim, because `Representation.dig` (`lib/graph_weaver/representation.rb`) does `return unless scope.is_a?(Hash)` at every hop — an Array fails that check and `dig` reports the path as simply absent, a message that looks like "you forgot a field," not "this is a list and dig doesn't loop." Calling it instead with a **single bare hash** (`line_items: {"sku"=>"a"}`, structurally wrong for a list field, and unable to express more than one line item) is **silently accepted**: `{"__typename"=>"Order","id"=>"o1","lineItems"=>{"sku"=>"a"}}`. `Representation.assign` can't produce anything else either — `parents.reduce(wire) { |scope, name| scope[name] ||= {} }` always builds a Hash at each path segment, never an Array, so even a fixed `dig` couldn't make `assign` emit a correct wire shape without further changes. Net effect: **the only value this builder can be persuaded to accept for a list-valued key field is one that misrepresents the entity** — a single object standing in for what the schema says is a list — and the one input shape a caller would reasonably reach for (mirroring the schema) is rejected with a message that blames the caller for an absent field rather than naming the real cause (a list where the builder expected an object). This is squarely the kind of silently-wrong-but-plausible-looking output the design principles call the most expensive failure mode this library can produce. Additive fix: `key_params` needs a third branch for a list-wrapped composite/enum key field, typed `T::Array[T::Hash[...]]` (or similar), and `Representation.dig`/`assign` need an Array-aware path step.

## Progressive `@override` with a `label`

11:15 - **apollo-federation-ruby 3.10.3 cannot express `label:` at all** — grepped `field.rb#add_v2_directives`: `override[:from]` is read, `override[:label]` never is. `field :popularity, Integer, null: false, override: { from: "legacy", label: "percent(50)" }` silently drops the label; `federation_sdl` prints only `@override(from: "legacy")`. Not a graph_weaver bug (same class as senior C's Finding #5 / senior F's orphan_types-omission: an apollo-federation-ruby footgun), but it means a Ruby subgraph team literally cannot roll out a progressive/canary override through this dependency's DSL — hand-written SDL is the only way, which is what I did next.
11:20 - Hand-composed `legacy`/`modern` subgraphs (`tmp/h/legacy.graphql`, `tmp/h/modern.graphql`) with `popularity: Int! @override(from: "legacy", label: "percent(50)")` on modern. Real `@apollo/composition` output (ground truth, not assumed):
```
popularity: Int! @join__field(graph: LEGACY, overrideLabel: "percent(50)") @join__field(graph: MODERN, override: "legacy", overrideLabel: "percent(50)")
```
**Composition keeps BOTH sides as resolvable `@join__field`s** when a label is present — a sharp contrast with senior F's finding that a *plain* (unlabeled) `@override` drops the losing side's `@join__field` entirely. Progressive override is structurally different in the supergraph, not just a metadata footnote on the same shape.

**Finding — HIGH — the local router silently, permanently routes 100% of a progressive-override field to one fixed side, with zero signal that anything unusual is happening, and the routing table's own `override` field is provably dead code.**
- `GraphWeaver::SchemaLoader.routing_table` reads `overrideLabel` **nowhere** — `RoutingTable::Field` has no `contextual`-style slot for it, and `read_fields`'s `applied.filter_map { |d| argument(d, "override") }.first` only ever reads the plain `from:` string. Grepped the whole `lib/` tree for `.override` outside the struct definition itself: **nothing reads `Field#override` anywhere** — not the planner, not `Federation::Drift`. It's captured and never consulted; pure dead data.
- Because both `@join__field`s are resolvable and neither is `external`/`usedOverridden`, `table.owners("Product","popularity") => ["legacy", "modern"]` — **both**, silently, with no warning and no entry in `#unsupported`.
- Ran it for real (`tmp/h/progressive_override2.rb`, both subgraphs loaded, `popularity` = 0 in legacy / 42 in modern): `router.execute('{ product(upc:"p1"){ popularity } }')` five times in a row, same process — **always** `trace=["legacy"]`, **always** `data.product.popularity == 0`. Never once touches modern, because `internal/planner.rb`'s `root_steps`/`plan_step` just takes `owners.first` (or whichever subgraph a prior fetch already landed on) when a field has multiple owners, exactly the same code path a `@shareable` field uses. `@shareable` sharing being arbitrary is *correct* there (both sides answer identically by contract); here the two sides are declared to answer *differently* on purpose (that's the entire point of a canary), and the router picks the "from" side 100% of the time, forever, with no way to observe it happened short of noticing the trace never says "modern".
- `federation:diff`/`Drift` sees nothing wrong either: `GraphWeaver::Federation::Drift.new(supergraph:, subgraphs: {legacy:, modern:}).report => "matches the schemas here (checked 2 of 2 subgraphs)"`.
- Directly answers the brief's question: **not refuse, not (visibly) ignore — silently pick one side, 100% of the time, forever**, which is a stronger and more surprising claim than "ignore the label" — a reader expecting *some* variance (even random 50/50, even always the *new* side) gets neither; they get a router that is functionally indistinguishable from `modern` never having shipped. This is exactly the category of failure the design principles name as the worst outcome ("A silent wrong answer is the most expensive outcome this library can produce, because the generated code looks authoritative") and the refusal table has no entry for it at all — a shared-ownership field split only by a label the table can't read should arguably be `unsupported_federation` (the table genuinely can't attribute the field, same reasoning as `@interfaceObject`/`@fromContext`) rather than silently answered as if it were `@shareable`. Additive fix: either read `overrideLabel` and raise a distinct `Unplannable` category for it (cheapest, matches the existing "refuse rather than guess" pattern used for `@fromContext`/`@interfaceObject`), or document explicitly that a progressive override always resolves to whichever side is *first* in `@join__field` order (empirically the `from:` side) under `:router`.

## `@context` / `@fromContext` (federation 2.8)

11:35 - apollo-federation-ruby has zero DSL for this either (confirmed by grep earlier); hand-wrote SDL. Real composition (`compose_raw.mjs`) confirms Apollo requires the field using `@fromContext` to live on a type with a resolvable `@key` (tried it on a plain, unkeyed `Size` first: `composeServices()` refuses outright — `"Object \"Size\" has no resolvable key but has a field with a contextual argument"` — a composition-level constraint, not graph_weaver's). Once `Size` also carries `@key(fields:"id")`, composition succeeds and — confirmed empirically, not assumed — **the argument itself is stripped from the field's public signature entirely** (`price: Int!`, no arguments at all in the printed supergraph type) and re-encoded as metadata: `@join__field(graph: SHOP, contextArguments: [{context: "shop__productContext", name: "countryCode", type: "String", selection: " { countryCode }"}])`. `RoutingTable#field("Size","price").contextual => ["countryCode"]` reads it correctly via the existing `context_arguments` parser.

**Crossing a subgraph boundary to reach a `@fromContext` field: refuses exactly as documented, confirmed with a real 2-subgraph cross.** `product_ctx` owns `Product`+context, `pricing_ctx` owns `Size.price`; `router.execute('{ product(id:"1"){ sizes { value price } } }')` raises `Unplannable(category: :context_argument)` verbatim: `"Size.price takes \"countryCode\" from a @context an ancestor selection sets, and the router would have to fetch it on its own"`. Matches `docs/federation.md`'s refusal table row exactly.

**Finding — CRITICAL — when the WHOLE subtree resolves in a single subgraph, the router does NOT "set its own context" as the docs claim — it silently drops the `@fromContext` argument and sends `nil`, producing a plausible-looking WRONG answer.**
Repro (`tmp/h/context_check.rb`, one subgraph `shop` owning both `Product` and `Size`): `router.execute('{ product(id:"1"){ countryCode sizes { value price } } }')` does **not** refuse. The `Size#price` resolver is called with `country_code: nil` (confirmed by an inline print in the resolver) even though `Product.countryCode` — the ancestor value a real gateway would read and inject — is right there in the same fetch, resolved moments earlier as `"US"`. Result: `sizes: [{value: 10, price: 500}, {value: 12, price: 600}]` where the resolver's own logic (`country_code == "US" ? value*100 : value*50`) means the CORRECT answer (had the router behaved like a gateway) would have been `price: 1000` / `1200` — **the response is silently wrong, not refused, not flagged**, and reads as a completely ordinary, successful `data` payload.

Root cause, precisely: `internal/planner.rb#contextual!` (the ONLY place `Field#contextual` / the `context_argument` refusal is ever raised) is called from inside `plan_step` (line 355, the per-node walk used when a query crosses a subgraph boundary). But a query whose entire tree resolves in one subgraph takes the `single_subgraph` shortcut (`internal/planner.rb` — the whole operation goes over **verbatim**, per docs/federation.md: "An operation that resolves in one subgraph goes over verbatim"), which never calls `plan_step` and therefore never calls `contextual!` at all. The code comment on `contextual!` even says this out loud and gets the consequence backwards: *"Asked only of a field the planner routes itself: a subtree handed to one subgraph whole carries its own context, which is why the verbatim path never reaches here."* The verbatim path does not "carry its own context" — it carries **no** context, because nothing in the verbatim path ever reads `@join__field`'s `contextArguments` or does anything with them; the client's original query document (which never mentions `countryCode` — that argument doesn't exist in the API schema at all, per the strip above) is simply forwarded as-is, and graphql-ruby resolves the optional argument to its default (nil, here). This is a straightforward gap, not a design tradeoff: the fix is to run the SAME `contextual!` check (or an equivalent one) over the verbatim path's selection set before handing it off, so a single-subgraph query touching a `@fromContext` field refuses exactly the same way a crossing one does — the "it resolves within the ancestor's own subgraph" case is not actually easier to get right; if anything the fact that the client can't even supply `countryCode` explicitly (it's stripped from the API schema) means there is no manual workaround for a caller either. Given the "refuse rather than guess" design principle this project states explicitly, and that a `@fromContext`-using type is *required* by Apollo's own composition to carry a resolvable `@keyent` (so this shape is not exotic — it's the *only* legal shape), this is the single highest-severity finding in this pass: it inverts the library's own stated worst-case-avoidance guarantee for a federation-2.8 construct that docs/federation.md explicitly claims to handle ("a subtree one subgraph answers whole ... plans normally").

## Abstract types across subgraphs

12:00 - **Interface implemented in two subgraphs where only ONE implementer is an entity — clean, no bug.** `Purchasable` interface implemented by `Bundle` (`@key(fields:"id")`, entity) and `Coupon` (no key at all, plain type) in one subgraph (`catalog2`); a second subgraph (`extras`) extends `Bundle` only (adds `discountCode`) and has no notion of `Purchasable`/`Coupon` at all. `table.possible_types("Purchasable","catalog2") => ["Bundle","Coupon"]`, `table.possible_types("Purchasable","extras") => []` (extras never implements the interface, correctly empty rather than nil), `table.entity?("Bundle") => true`, `table.entity?("Coupon") => false`. `router.execute('{ purchasables { id label ... on Bundle { itemCount discountCode } ... on Coupon { percentOff } } }')`: trace `["catalog2","extras"]`, correct data for both — `Bundle` crosses into extras for `discountCode`, `Coupon` (no key, no second subgraph) never attempts a cross at all. The bucket-per-concrete-type mechanism (`plan_branches`) only builds a `Branches` entry, and only fetches elsewhere, for the concrete type that actually needs it — a non-entity sibling in the same abstract type is simply inert with respect to crossing. No bug; this is the interface analogue of the `@key(resolvable:false)` result above, and behaves exactly as that mechanism would predict.

12:10 - **Union with 3 members across 2 subgraphs, one member `@inaccessible` — clean, and confirms a real asymmetry that's harmless by construction.** `SearchResult = Article | InternalDoc | Video`; `Article`+`InternalDoc` in `search_a` (InternalDoc marked `@inaccessible`), `Video` in `search_b`. `SchemaLoader.load` (client-facing `@schema`, used for query validation/codegen) correctly drops `InternalDoc`: `schema.types["SearchResult"].possible_types => ["Article","Video"]`, `schema.types["InternalDoc"] => nil`. `SchemaLoader.routing_table` (the RAW, unstripped read used for planning) still knows about it: `table.possible_types("SearchResult","search_a") => ["Article","InternalDoc"]`, `table.declares?("InternalDoc") => true`. **This is a real asymmetry — the table the router plans against carries strictly more than the schema a client can query against — but it's provably harmless**: a hand-written query naming `... on InternalDoc` fails at generation time before it ever reaches the router (`GraphWeaver::QueryValidationError: "No such type InternalDoc, so it can't be a fragment condition"`, since validation runs against the stripped `@schema`), so the table's extra knowledge is simply never exercised by anything a real client (or a spec) can express.
