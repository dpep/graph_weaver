## FINDINGS

### F1 (HIGH) — local router never tags a bubbled subgraph error as subgraph-origin; both real transports always do
Repro: `{ product(upc: "p3") { name shippingEstimate } }` (reviews' shippingEstimate raises plain `GraphQL::ExecutionError, "carrier unavailable for this weight"`, no extensions set).
  local:   `{"data":{"product":null},"errors":[{"message":"carrier unavailable for this weight","path":["product","shippingEstimate"]}]}`
  gateway: `..."extensions":{"serviceName":"reviews","code":"DOWNSTREAM_SERVICE_ERROR","stacktrace":[...]}`
  router:  `..."extensions":{"service":"reviews"}` (plus a separate `extensions.valueCompletion` diagnostic array)
Message and path match exactly everywhere (the actual failure mode IS caught correctly). What's missing locally is the router-synthesized metadata a client commonly branches on to tell "this failed downstream" from an ordinary business error — `extensions.code === "DOWNSTREAM_SERVICE_ERROR"` or `extensions.service`/`serviceName`. Confirmed this is specific to router-synthesized metadata, not extensions in general: a resolver that sets its OWN extensions (`Reviews::Query.boom` raising with `extensions: {"code"=>"ROOT_BOOM"}`) round-trips identically on all three (`local: ...{"code":"ROOT_BOOM"}` verbatim, gateway/router both add serviceName/service ON TOP but keep ROOT_BOOM intact). So the interface design ("errors are part of the interface") is honored for what a subgraph author writes — the gap is purely the router's own "which subgraph did this" stamp, which real transports always add and the local one never does. A test asserting on that stamp passes here, in dev, and would be the first thing to break in front of a real gateway.
Fix (additive): tag each re-emitted subgraph-origin error with `extensions: {"service" => name}` (matching the modern router's field name, since @apollo/gateway is deprecated) unless the subgraph already set its own `extensions.service`/`serviceName`. Doesn't invent a `code` the subgraph didn't provide.

### F2 (HIGH) — "a real router" is not one thing; the two real Apollo transports disagree with each other on most of what this brief probed
Same supergraph, same subgraphs, three-way comparisons where gateway (@apollo/gateway, JS, deprecated) and Apollo Router (Rust, current) disagree with EACH OTHER, not just with graph_weaver:
  - subgraph HTTP 500: gateway gives ONE error (`"500: Internal Server Error"`, `code: INTERNAL_SERVER_ERROR`, subgraph body buried in `extensions.response.body`); router gives TWO errors — a synthetic `"HTTP fetch failed from 'reviews': 500: Internal Server Error"` (`code: SUBREQUEST_HTTP_ERROR`) AND the subgraph's own `"internal server error"` message surfaced as its own top-level entry.
  - malformed JSON: gateway — generic `"invalid json response body ... Unexpected end of JSON input"` (`INTERNAL_SERVER_ERROR`); router — `"service 'reviews' response was malformed: EOF while parsing a value at line 1 column 16"` (`SUBREQUEST_MALFORMED_RESPONSE`).
  - `@defer`: gateway rejects it at validation (`"Unknown directive \"@defer\"."`, GRAPHQL_VALIDATION_FAILED) — it simply doesn't know the directive. Router VALIDATES it fine and returns `406 {"message":"the router received a query with the @defer directive but the client does not accept multipart/mixed HTTP responses. To enable @defer support, add the HTTP header 'Accept: multipart/mixed;deferSpec=20220824'","extensions":{"code":"DEFER_BAD_HEADER"}}` — a fully supported, header-gated feature.
  - introspection: gateway answers `{ __schema { queryType { name } } }` with no config; router refuses by default (`"introspection has been disabled"`, `INTROSPECTION_DISABLED`) until `supergraph.introspection: true` is set explicitly.
  - diagnostics: router (only) adds a top-level `extensions.valueCompletion` array on every null-propagation case, describing exactly which field went null and why — neither gateway nor the local router does this.
None of this is graph_weaver's bug — but docs/federation.md's and the README's parity claims (and senior C's byte-identical DATA measurement) are built entirely on `@apollo/gateway`, which is the DEPRECATED transport. A team reading "run this one against a real router" and reaching for the CURRENTLY RECOMMENDED Apollo Router gets a materially different error shape, a working `@defer`, and introspection off by default — three surprises the existing docs don't flag, because the harness that produced the docs' own numbers never ran against it. Worth a line in docs/federation.md naming which "real router" the parity claims were measured against, since the two aren't interchangeable.

### F3 (MEDIUM-HIGH) — generalizes F(session)'s "no representation for timeout": the WHOLE wire-fault category is unrepresentable under `:router`, not just timeouts
Injected four subgraph-side failures at the WEBrick layer the real gateway/router talk to (HTTP 500, truncated/malformed JSON, `errors` with no `data` key at all, and a slow/hung response) against the identical query. Real gateway and router both degraded gracefully and differently (see F2); the LOCAL router returned the fully successful, undegraded answer in EVERY case:
  `{ product(upc: "p1") { name shippingEstimate } }` while reviews is "down" any of the four ways ->
  local: `{"data":{"product":{"name":"Table","shippingEstimate":120}}}` (unaffected, all four times)
Root cause, confirmed by design, not a bug: `Testing::Router` calls `@subgraphs.fetch(name).execute(...)` as a direct in-process Ruby method call on the schema CLASS (lib/graph_weaver/testing/router.rb ~line 671) — there is no transport to misbehave on. Senior F's session already found this for timeouts specifically; this run shows it's the general case: a local `:router` suite structurally cannot exercise "one subgraph is down/slow/returning garbage while its siblings still answer," for ANY of the ordinary ways a subgraph actually goes down — only application-level failures (a resolver that raises, or resolves to a bad value) are reachable, via monkeypatching the Ruby class. docs/testing.md's `:router` section frames the boundary purely in planning/routing terms; it doesn't have a line saying "wire-level subgraph faults need `:wire` + a `Failure` fake, or a real router" — worth adding, since it's exactly the gap a team discovers the hard way in an incident retro ("our tests all passed...").

### F4 (MEDIUM) — no explicit `@defer` refusal category; current rejection is incidental, not a deliberate guarantee
`Testing::Router::Unplannable::CATEGORIES` (lib/graph_weaver/testing/router.rb ~line 29) enumerates every deliberate refusal (`no_key`, `abstract_boundary`, `interface_object`, `context_argument`, `chained_requires`, `nested_field_set`, `conditional_fragment`, `undefined_fragment`, `unsupported_federation`, `too_deep`, `operation_type`) — there is no `defer` (or `stream`) entry. Querying `{ me { username ... @defer { reviews { body } } } }` locally fails with `"Directive @defer is not defined"` (GRAPHQL_VALIDATION_FAILED) — the SAME layering gap senior F already flagged for `undefined_fragment`/`operation_type`: it never reaches the router's planner at all, because the derived API schema simply doesn't declare the directive. That happens to look like "refuse by name" today, but it's an accident of what graphql-ruby's schema builder emits, not a decision the planner made. Confirmed the accident is fragile: the CURRENT real Apollo Router (F2 above) already treats `@defer` as a known, supported directive — the day graph_weaver's schema derivation (or a future federation-version bump) starts declaring `@defer` as a recognized directive too, this incidental rejection disappears, and the planner — which has zero `@defer`-aware code — has no dedicated fallback to catch it. Fix (additive): add `@defer`/`@stream` as an explicit, by-name refusal category (like `chained_requires`) so the guarantee survives a future schema change instead of depending on one.

## Design critique
The library's central bet — "faithful subset of a real router, refuse rather than guess" — holds up well for the ONE thing it was built to guarantee: when the local router DOES answer, the answer (message, path, data shape) matches a real router's, including in genuinely deep null-propagation and @requires/@provides edge cases this session added beyond what C/F already covered. Where it's thinner is the SECOND promise implied throughout the docs — "test against this instead of a real router" — because two things a team would reasonably expect to carry over don't: the metadata a client actually branches on (which subgraph failed) is synthesized by every real transport and by none of the local ones (F1), and an entire class of realistic failures (a subgraph that's down, slow, or returning garbage) has zero representation under `:router` and is only reachable via `:wire`+`Failure` fakes that this session's prior pass (F, session) already showed have their own sharp edges (single stubbed URL for the whole federated graph). Neither is a correctness bug in what the router computes; both are gaps in what "faithful" covers, and both are exactly the kind of thing that reads as "additive, not breaking" — tag errors with their origin subgraph, add `@defer`/`@stream` as deliberate refusals — rather than a design rework. The most surprising finding this session (F2) isn't about graph_weaver at all: "a real router" turns out to be two materially different things depending on which one a team picks, which means the honest fix isn't just "test against a real router" but "test against the SAME real router your docs' parity numbers were measured against," named explicitly.

## Would I ship on this surface?
Yes, for the same reason senior C and F both landed there: every divergence found across three sessions has been a documented-adjacent gap or a metadata omission, never a wrong answer where the local router said something confident and false. This session adds two things worth fixing before a team leans on it hard: tag subgraph-origin errors with which subgraph failed (F1) — cheap, additive, and it's exactly the field a real error-monitoring integration keys on — and turn the accidental `@defer` refusal into a deliberate one (F4), since "refuses by name" is a documented guarantee everywhere else in this router and shouldn't be true by luck in one spot. Neither blocks adoption; both are the kind of thing I'd file as follow-up issues on day one rather than treat as a reason to wait.
