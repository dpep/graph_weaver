## Step 7 (~9:45am) — read docs/errors.md IN FULL
This is the single most important doc for the task. Very detailed, no ambiguity for the client-side path. Key facts extracted:
- `execute` returns `GraphWeaver::Response[Result]` (never raises on GraphQL errors — this is Requirement 2.1's mechanism: errors+partial data both live on the same envelope, `response.data` + `response.errors` + `response.success?`).
- `execute!` raises `GraphWeaver::QueryError` on top-level GraphQL errors (== `execute(...).data!`).
- Client-side bad input (caught BEFORE the request is sent) raises `GraphWeaver::InputError`, with `#kind` (Symbol, one of 8, `GraphWeaver::InputError::KINDS`), `#path` (Array of Strings/indices, rooted at the variable), `#coordinate` (schema coordinate string or nil), `#value`, `#details` (kind-specific hash), `#field` (path's last NAMED segment — exactly what a form needs to highlight the right field), `#struct`.
- CRUCIAL for my Requirement-1 "does path point at the right list element" question: doc explicitly gives the exact table I need:
  - `execute(ids: [1, 2, "x"])` → `path: ["ids", 2]`, `coordinate: nil` (list element is a position not a slot) — this literally matches my type-names-list-with-a-number test case in advance!
  - nested filter: `execute(where: {_and: [{_not: {species: "LIZARD"}}]})` → `path: ["where", "_and", 0, "_not", "species"]`, `coordinate: "PetFilter.species"` — this is EXACTLY the nested pokemon_v2_pokemontypes/pokemon_v2_type/name shape I need to test.
- Server-side rejection: `response.input_errors` reads GraphQLErrors that are "about input" back into the SAME InputError class — one renderer for both client- and server-caught cases. Table of which servers are recognized: graphql-ruby (variable-coercion problems array or 4 rule-name extensions.code), Apollo (BAD_USER_INPUT), **Hasura** (extensions.path naming an argument under validation-failed/parse-failed) — GREAT NEWS, PokeAPI IS Hasura, so this table applies directly to my target API. Hasura only gets `:not_a_member`/`:unknown`/`:missing` kinds from its 3 fixed sentences, `:refused` otherwise (e.g. `limit: -5` comes back `:refused`, not `:out_of_range`, per the doc's own worked example — this literally answers my "negative limit" test case in advance: I should expect a `:refused` kind from Hasura, NOT `:out_of_range`, since Hasura's "expected a non-negative 32-bit integer" sentence isn't in the closed table).
- Cast failures (drift): `GraphWeaver::CastError` — `#struct`, `#cause`. Doc explicitly says how to simulate one in tests: `GraphWeaver::Testing::FakeClient.new(schema:, corrupt: "Person.birthday")` — this answers Requirement 2.2 exactly. Need testing.md for the full recipe/tag form.
- Doc is dense but not confusing — it front-loads a table (which class, when) then goes deep on InputError since that's the meaty one. No contradictions found. One thing I'll watch for: "eight kinds" but only saw 4 named directly here (`not_a_member`, `refused`, `out_of_range`, `invalid_format` — plus presumably `unknown`, `missing` from the Hasura table). Full list should be in i18n.md, reading that next.

- Building the search as a JSON-friendly POST endpoint (`PokemonSearchesController#create`) rather than a plain GET form, so the "list contains a number" and "nested wrong shape" bad-input tests can actually happen (a GET query string can't carry a JSON number inside an array — everything in a query string is a string). ## Step 13 (~10:50am) — hit a real environment bug, NOT graph_weaver's fault
- Tried to POST a JSON body (`Content-Type: application/json`) to test cases 4 (list w/ wrong element type) and 5 (nested wrong shape), since a query-string/form-encoded POST can never carry a non-String array element (every value in a URL-encoded form is a string). Got a bare 400 Bad Request with no useful page.
- Dug in with `rails runner` + manual `ActionDispatch::Request` construction (this is investigating MY Rails env, not graph_weaver — logging for completeness/honesty per the task's ground rules). Root cause: `ActiveSupport::JSON.decode` calls `::JSON.parse(json, options)` with 2 args, but the `json` gem installed here (3.0.2) only accepts 1 (`JSON.parse(source)` — no options hash). `wrong number of arguments (given 2, expected 1)` in `json-3.0.2/lib/json/common.rb:296`. This is a straight-up Rails 8.1.3.1 / json gem 3.0.2 version-skew bug in this sandbox's gem set — confirmed by testing `JSON.parse('{"a":1}')` directly (works fine) vs posting the same body through Rails' request-parameter pipeline (breaks every time, even for a body with no array at all). **Nothing to do with graph_weaver** — this would break ANY Rails JSON API endpoint in this exact gem combination, whether or not graph_weaver is in the Gemfile.
- Per the task's time-box instructions: tried the direct fix path once (could I bump the `json` gem?) — decided against it since (a) it's not my app's job to fix the platform's Rails/json compatibility, (b) the task says work is scoped to this environment as given, and (c) there's a clean workaround that still genuinely exercises graph_weaver's InputError machinery through real HTTP without touching Rails' broken JSON-body parsing at all: accept the two "raw" fields that need non-string / wrong-shaped values as separate form fields holding a JSON-encoded STRING (`type_names_json`, `pokemon_v2_type_json`), and call plain `::JSON.parse` on them myself inside the controller — a normal `application/x-www-form-urlencoded` POST, so Rails' JSON body-parsing code path is never invoked, only my own direct `JSON.parse` call (proven to work standalone).
