# Senior G: custom scalars beyond one graph, and under the type checker

Read /tmp/claude/graph_weaver/brief-senior2-common.md. Prior passes: senior A (/tmp/claude/graph_weaver/senior-log-A.md — registration, Money, equality) and senior D (/tmp/claude/graph_weaver/senior-log-D.md — inputs, modes, to_json, precision). Both sets of findings are fixed on main; don't redo them. App dir `senior-app-G`, log `senior-log-G.md`.

Your angle is scalars where the registry meets MORE THAN ONE graph, and where the generated code meets `srb tc`.

- **Registry is global, graphs are many.** Declare two graphs in one app (an in-process graphql-ruby schema and the live Countries API, or PokeAPI): both declare a scalar named `DateTime` — one as ISO-8601, the other as epoch millis. Register per docs. What happens: one registration wins silently, a refusal, or a per-graph door you have to find? Same for an enum name shared by both graphs with different members, and for `extend_type` on a type name both graphs have. Then a scalar registered for graph A only, used by a query in graph B — what does generation say. Then `rake graph_weaver:graphs` and `verify` — do they tell you which registrations apply to which graph.
- **Static typing of the generated output.** Run `srb tc` (add sorbet + tapioca to the app) over generated modules with every registration door: class, type-string, object scalar, `cast:` proc, `fallback:` enum, mapped enum, `T::Enum`, `extend_type` mixin with its own sigs. Which produce a `T.untyped` prop, and does the doc say so? Write app code that misuses each (call a method on a nilable scalar, pass a wrong type as a variable, compare a `T::Enum` to a string, index a mapped enum's fallback) and record what `srb tc` catches vs what only runtime catches. Then the drift case: the server adds a value to an enum you mapped — generated code, `srb tc`, runtime, in that order.
- **Registration lifecycle.** A registration in `config/initializers` vs `to_prepare` vs an `after_initialize`, under `rails generate`, `rake graph_weaver:generate`, `verify`, and a dev-mode reload (`rails runner` twice, `Rails.application.reloader.reload!`): which registrations are visible when, and does `verify` ever pass while generation would have differed. A registration that raises during boot. Registering the same name twice with different classes (a warning, a refusal, last-wins?).
- **Cassettes and fakes across registrations.** Record a cassette with one registration, change the registration, replay: what fails, and does it name the registration. A `:fake` pin whose value is the Ruby object vs the wire string for the same scalar.
