**K1 (HIGH) — `Retry` and `throttled?` never fire behind a router.** Measured: router `traffic_shaping.router.global_rate_limit` answers `HTTP 503 {"errors":[{"message":"Your request has been rate limited","extensions":{"code":"REQUEST_RATE_LIMITED"}}]}`; `Transport#perform` returns the parsed body on any non-2xx carrying errors, so no `ServerError`; `Retry.new(transport, retries: 3)` → 1 attempt; `retry_codes: THROTTLE_CODES` → 1 attempt because `REQUEST_RATE_LIMITED` isn't in the list whose comment claims Apollo; `QueryError#throttled?` false. Also a router-internal 500 with an errors body and a 200 `GATEWAY_TIMEOUT`. Candidates: (a) `Retry#retryable_response?` reads the HTTP status the transport already knows (`payload[:http_status]` is set two lines before the body is returned — surface it on the parsed response or the QueryError) and applies the same status rule it applies to `ServerError` (5xx, 408, 429), plus the body's codes; (b) keep body-wins and only extend the codes. (a) is the rule "a retryable status is retryable whether or not the body parsed", one sentence, and it makes `retry_mutations` still govern mutations. Add `REQUEST_RATE_LIMITED` to `THROTTLE_CODES` either way, and decide whether `GATEWAY_TIMEOUT` (a 200) belongs in a retryable-code list (the senior's P5a: partial data was kept — retrying a partial success is a judgment; say yours). Specs: each measured shape through `Retry`, attempts counted, watched failing first. Fix docs/errors.md's table ("`QueryError` is a 200 body with top-level errors" is false behind a router) and the `rescue ServerError` idiom it shows.
