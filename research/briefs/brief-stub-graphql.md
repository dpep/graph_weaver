**The design, one rule.** `stub_graphql(key).to_return(value)` is one pin: the key is anything a pin already accepts (a type name, a `"Type.field"` coordinate, a bare field name), the value is anything a pin already accepts (a wire value, a Ruby object read field by field — a FactoryBot build — with the rest fabricated, a registered scalar's Ruby object which `serialize:` carries to the wire). It reads the way WebMock reads and it says the thing `graphql_fake("User.me" => user)` says today. Under `graphql: :fake` it pins the example's fake; under `graphql: :router` it pins the router's `fake:`. `to_return` is the only verb — no `.with`, `.to_fail`, `.times`; the report may argue for one if the dogfood shows a need, but don't build it. An operation-scoping first argument is out of scope; note in the report whether anything in the dogfood wanted it.

**Build.** In `lib/graph_weaver/rspec.rb` beside `graphql_fake`, reusing the same per-graph pin table `graphql_fake` writes into (`graph:` keyword accepted the same way for a multi-graph app). A stub with no `to_return` by the time the example runs is a refusal naming the key. A key the schema doesn't know is the same spellchecked refusal pins already give. Specs in `spec/rspec_spec.rb`, watched failing.

**Dogfood, three places, report what each showed.**
1. **The repo's own specs**: convert every `graphql_fake(...)` and `graphql_router(fake: ...)` call site whose pins are the point of the example to the new spelling (keep the mode helpers where they are about mode or options). Count the sites; say whether each read better, worse, or the same, and quote two before/after pairs.
2. **A Rails app with real objects**: copy `/tmp/claude/graph_weaver/senior-app-E` (an in-process schema with validation, request specs) or `junior-app-15` (two remote graphs) to `stub-app`, repoint the Gemfile at your worktree, add FactoryBot, and write specs that stub with a built object: a flat object, an object with a `has_many` the query selects nested (`user.orders` → `User.orders { status total }`), an object carrying a registered scalar (`Money`, `Date`), an object missing a selected field (fabricated? refused?), an object with an extra method the query doesn't select. Record exactly what the object-pin reader does with each — this is the "does serialization hold" question, and nesting is the one nobody has verified.
3. **The `:wire` layer**: under `graphql: :wire`, `stub_graphql` beside WebMock's `stub_request` — is which stub answers which question obvious from the spec, and what one sentence would the docs need.
