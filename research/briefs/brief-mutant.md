# Lane: mutation testing

Read /tmp/claude/graph_weaver/brief-common.md for toolchain, gate, trailers. Baseline: main **4fd16d2** (you are in a worktree off it). CHANGELOG lane marker `<!-- lane: mutant -->` under `###  Unreleased` only if anything user-visible changes (a spec-only lane usually has no entry). Every gate command its own Bash call.

You are the engineer who believes a test nobody has watched fail is only an assertion. The suite is 1777 examples at 98% line coverage, and this release's rule has been "verify the spec fails before the fix", enforced by briefing. Make it mechanical for one pass: run mutation testing over the runtime code users' apps execute and turn surviving mutants into either a sharper spec or a report that the code is dead or equivalent.

Tool: the `mutant` gem (`mutant-rspec`); check its current license terms and Ruby 3.4 support before adding it. Add it to the `Gemfile` development group (not the gemspec), pin it, update `Gemfile.lock` with a frozen-compatible `bundle install`. If mutant can't run here (sorbet-runtime sigs wrapping methods is the likely obstacle; `T::Configuration` has switches to disable runtime checking), say what broke and try the fallback: a hand-rolled pass where you flip each branch in the subject file one at a time and see whether the suite notices. Either way the deliverable is the same list.

Subjects, in this order, stop when time says so: `GraphWeaver::Coerce`, `GraphWeaver::InputStruct`, `GraphWeaver::ResultStruct`, `GraphWeaver::Response`, `GraphWeaver::Hints`, `GraphWeaver::Inflect`, `GraphWeaver::Retry`, `GraphWeaver::Internal::Redact`, `GraphWeaver::InputError` and the server-input arms in `internal/server_input.rb`. Not the codegen walk (dynamic, covered by the round-trip property harness), not the rake tasks, not the railtie.

For each surviving mutant, one of three outcomes, recorded: (1) a spec that kills it, written as a behavior a user would care about, not `expect(x).to eq mutant_bait`; (2) equivalent mutant, one line why; (3) dead or unreachable code, reported with the line, don't delete it, another lane may own the file. Keep specs focused: one example per behavior, and if killing a mutant would need a contrived example, prefer outcome (2) or (3) and say so. Do not edit any file under `lib/` except to delete code you prove dead AND that no other lane owns: `coerce.rb`, `hints.rb`, `inflect.rb` belong to the corpus lane right now, `retry.rb` and `redact.rb` to the transport lane, so for those report only. `input_struct.rb`, `result_struct.rb`, `response.rb`, `errors.rb`'s InputError arm, `internal/server_input.rb` are yours for dead-code deletion only.

Ownership: `Gemfile`, `Gemfile.lock`, `.mutant.yml` or equivalent config, `spec/**` for the subjects above (add examples to the existing spec file for each subject; a new file only if none exists), `CLAUDE.md` one sentence on how to run it if it works, `CHANGELOG.md` (your block, if any). Not yours: `lib/**` beyond the dead-code rule above, `docs/**`.

Gate: brief-common's (rspec random seed, `srb tc`, `bin/generate` clean), two random seeds, and `bundle install --frozen` or the CI equivalent succeeding with the new lock (CI runs a frozen install and fails at setup with exit 16 if the lock is stale). Report to `/tmp/claude/graph_weaver/mutant-report.md` and in your final message: whether mutant ran and how; per subject the mutant count, killed before, killed after, and the survivors by outcome; the dead-code list for files you don't own; the mutation score per subject rounded to the precision it has; shas; `git status` clean.
