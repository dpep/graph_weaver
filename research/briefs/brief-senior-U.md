Read /tmp/claude/graph_weaver/brief-round6-common.md. App dir `senior-app-U`, log `senior-log-U.md`. Scalars have been driven as a client (A, D, G, M). You are the graphql-ruby SERVER author whose team also consumes its own API through graph_weaver, so every scalar has two definitions that must agree: the server's `coerce_input`/`coerce_result` and the client's `register_scalar`. Your question is whether the gem helps keep them in lockstep or lets them drift silently.

- Define eight scalars on the server side with real, opinionated coercions: `Money` (object `{amount, currency}` out, string `"12.50 USD"` accepted in), `DateTime` (RFC3339 with offset out, epoch millis also accepted in), `Decimal` (string out, never a JSON number), `URL` (normalized on input), `Slug` (lowercased on input), `Email` (validated, raises `GraphQL::CoercionError`), `JSON` (passthrough), `Duration` (ISO 8601). Register each on the client per docs/scalars.md, `:in_process` against the same schema class so both sides run in one process.
- **Lockstep**: for each scalar, a value that the server accepts but the client's `serialize:` never produces (epoch millis for DateTime); a value the client produces that the server rejects (`Money` as a bare decimal); a `coerce_result` change on the server (Decimal → number) with the client unchanged — what catches it (`verify`? `schema:diff`? nothing, since the scalar's *name* is unchanged?), and at what layer the mismatch surfaces (a `CastError` naming the field? a silently wrong Float?). This is the finding this brief exists for: a scalar's wire contract lives in two `coerce_*` methods the schema dump cannot see.
- **`CoercionError` round trip**: the server's message for an invalid `Email` through `execute`, `execute!`, `input_errors` — kind, path, whether the server's own message survives redaction intact (it is the server's words, documented pass-through).
- **Scalars in `@oneOf` inputs and in list-of-input arguments** with server-side `validates:` on the scalar field; a scalar default value in the schema (`amount: Money = "0 USD"`) — generated code, and whether the client sends the default or omits the argument.
- **The fake and cassettes from the server author's seat**: `:fake` fabricates a `Money` — from the client registration only; does it ever produce a value your server would reject, and does `:in_process` catch what `:fake` fabricated wrong? A cassette recorded against `:in_process` after the server tightened `Email` — replay passes; `cassettes:check` says what.
- **Introspection of scalars**: `specifiedByURL` on a scalar (GraphQL 2021+), a description — do they reach the dump and generated code (as a comment? as `specified_by`?), and does `schema:diff` report a description change.
Report the matrix, the drift table (what changed on the server → what the client noticed → at what layer → with what message), and what a lockstep check would need to read that nothing reads today.
