## The gap (PLAN.md item 1)

`execute.graph_weaver` is one REQUEST: one attempt, whichever client served it,
closed when the parsed response is back. Two things it structurally can't say:

- A `CastError` happens after the request returned, so the event closes `:ok`
  and then the caller gets an exception. The dashboard says success; the app saw
  a failure.
- The testing doubles (`FakeClient`, `Testing::Router`, cassettes) emit no
  request event, so a spec asserting on instrumentation can't run under any
  `graphql:` tag.

Moving the request event's extent up would collapse `Retry`'s per-attempt events
(`:retries`, per-attempt `:http_status`), which subscribers rely on. So: a second
event, at the module seam.

## The design (lead's lean — improve it, don't just execute it)

- **Name**: `operation.graph_weaver` (`GraphWeaver::OPERATION_EVENT`): one call of
  one generated module's `execute`/`execute!`, start to typed result or raise. The
  request event nests inside it (one or more, under Retry). Pick another name if
  the ecosystem's spelling argues for it (`sql.active_record` /
  `execute_multiplex.graphql` are the precedents the existing name follows).
- **Fired where every client kind passes**: the module seam, so fakes, routers,
  in-process and wire all emit it. That means the generated `execute` calls a
  runtime method that wraps dispatch AND the cast. Today `execute` is
  `from_response(dispatch(variables, client:))`, both halves generated; the
  smallest change is `dispatch` taking the cast as a block
  (`dispatch(variables, client:) { |raw| from_response(raw) }`) with the event
  wrapping both. That changes emitted code → **Action: Regenerate**, and a module
  generated by 0.7.5 keeps working and simply emits no operation event until
  regenerated — say so in the docs and changelog. If you find a way that needs no
  emitted-code change, prefer it and say what it costs.
- **Payload**, every key filled before the block returns, mirroring the request
  event's discipline: `:operation` (name), `:module` (the generated module's name —
  the one thing this seam knows and the request seam doesn't), `:graph`, `:kind`,
  `:client` (the class that served it — for a fake, the fake), `:status` — `:ok`
  (typed result), `:errors` (the response carried GraphQL errors; what `execute!`
  raises `QueryError` for), `:failed` (raised: transport, `CastError`, anything) —
  `:error` (class name, on `:failed`), `:code` (as the request event defines it, on
  `:errors`), `:duration_ms` — the caller's wall clock: dispatch, every retry and
  its backoff, and the cast. NOT `:url`, `:http_status`, `:retries` — those are
  attempt facts and stay on the request event. Never query text or variables.
- `from_response` called directly (a raw hash from another client) emits nothing:
  no call happened. State it.
- `GraphWeaver::LogSubscriber` (one line per operation) today attaches to the
  request event. Decide whether it should read the operation event instead (it
  would then say the truth about a cast failure, and log under fakes) — and if
  that changes what a line says or when it appears, that is a user-visible change
  with its own bullet. Lead's lean: move it, keep the line format, and keep the
  per-attempt facts at debug.
- `docs/logging.md` gets the second event with its own payload table and one
  sentence on how the two nest; the OTel/Datadog snippets say which event they
  trace (a span per operation with attempt spans inside reads well).
