**#1 (HIGH) — block-form `extend_type("Widget") { ... }` inside a `GraphWeaver.graph` block mints a fresh `GraphWeaver::TypeHelpers::WidgetVn` on every registry read.** `codegen/type_helpers.rb` ~131: `name = "#{base}V#{count += 1}" while const_defined?(name)` then `const_set(name, Module.new(&block))`. A graph's registry is read at declaration-time validation and on each `generate!`/`verify_generated!`, so `rake graph_weaver:generate` bakes `WidgetV3` while `rails server` (one read) creates `WidgetV1`: boot fails with "includes GraphWeaver::TypeHelpers::WidgetV3, but nothing registers it" and `verify`, run moments before on the same tree, said up to date. Root cause is in `graph.rb`/`internal/graph_builder.rb` re-running registrations per read as much as in the minting. Decide the rule: a registration block is evaluated once per graph declaration and the module it makes is the one every read returns (memoize the built module on the registration, keyed by graph + type — the top-level, non-graph registry presumably already behaves this way; make the graph path match it), so the name is stable across reads and across processes for the same source. If the name must still be derived, derive it from something stable (graph name + type), never a counter. Spec: read the registry three times and generate, assert the same module name every time, and a spec that the name is stable across two fresh `GraphWeaver.graph` declarations of the same source in the same process (the reload case). Watch them fail first. Then in the app: `rake graph_weaver:generate` → `rails runner` boots and executes → `verify` agrees.

**#2 (MEDIUM) — `result.tier == "GOLD"` is silently false.** A generated `T::Enum` compared with its wire string answers false with no signal. Decide: emit `==` on generated enums that raises a `GraphWeaver::CastError`-family or `TypeError` naming the enum and the member to compare with (`Tier::Gold`) when the other side is a String — "refuse rather than guess" — or leave `T::Enum` semantics and document. Check what sorbet-runtime's `T::Enum#==` does with `T::Configuration.legacy_t_enum_migration_mode` (it can warn) before adding anything; if a one-line configuration gives the warning under the app's control, prefer documenting that over a generated override. Say which and why.
