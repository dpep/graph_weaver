# Translating input errors

> **Status: proposed, not shipped.** Nothing on this page works yet. It
> describes the keys and the data a future release would expose so an app can
> translate "that input was wrong" without reading English sentences. Today the
> machine side of an input failure is `#field` (the *variable*, not the field
> inside it) and `#struct` — see [errors](errors.md). Read this to say yes or no
> to the shape before it becomes permanent.

## The one idea

A library that hands you a sentence has already decided what your user reads, in
one language, in its own voice. So graph_weaver should hand you **a stable key
and the facts**, and let the app own the sentence:

- **stable** — a `kind` from a short closed vocabulary, and the key derived from
  it, `graph_weaver.input.<kind>`. These are API: they change only with a MAJOR
  bump, and a new one arrives only as an addition.
- **data** — the field, the value, the enum's members, the bounds. Never baked
  into the message only, and never pre-formatted (`members` is an Array, not
  "CAT or DOG" — joining it is a language decision).
- **not stable** — `#message`. It is the developer's line, in English, and it
  will be reworded.

## The vocabulary

Eight kinds, each one sentence. A ninth arrives only when a real input failure
fits none of them — `:refused` is the honest home for everything else.

| `kind` | means | `details` carries | client | server, free | server, convention |
|---|---|---|---|---|---|
| `:type_mismatch` | the value is not the type the schema declares, and no conversion applies | `type` | yes | yes | yes |
| `:unparseable` | the right kind of thing, but the text doesn't parse as that scalar | `type` | yes | yes | yes |
| `:not_a_member` | not one of the values an enum (or an inclusion rule) allows | `members` | yes | yes | yes |
| `:missing` | a required field or argument wasn't supplied, or was null | — | yes | yes | yes |
| `:unknown` | a key the input type doesn't define — a typo | `suggestion` | yes | yes | yes |
| `:out_of_range` | a number, length or date outside the bounds the schema states | `min`, `max` | **no** | **no** | yes |
| `:invalid_format` | parses, right type, but fails a stated semantic rule — a regex, an email | `format` | **no** | **no** | yes |
| `:refused` | rejected, with nothing more than a message — the fallback, never a guess | — | yes | yes | yes |

`field` and `value` ride on every kind. `value` is the offending value passed
through [`filter_parameters`](logging.md#filtered-variables), so it reads
`"[FILTERED]"` under a sensitive key and `nil` when the producer never said what
the value was.

Two rows carry the headline: **`:out_of_range` and `:invalid_format` — the
customer's "right type but out of range" and "bad semantic format" — cannot be
produced today from either side without the server convention below.** The
client doesn't know the schema's bounds, and a graphql-ruby `validates:` failure
reaches the wire as a bare sentence with no `extensions` at all.

`@oneOf` violations map to `:refused`. The message is already specific ("supply
exactly one field, non-null, got a, b"), and one rule in twenty schemas doesn't
earn a ninth kind.

## The shape

One value object, carried by both halves — not one class, because the two halves
are not one thing. `InputError` is *raised*, once, before the request leaves, and
rescuing it is a control-flow decision (render a 422). A server-side input
problem arrives N-at-a-time inside a 200 response that may also carry partial
data, and is never raised on its own. Folding them into one class would mean
either a raisable collection member or an `InputError` that isn't an exception —
the first is a lie about control flow, the second breaks the documented 422
rescue. What they genuinely share is the *shape of a field problem*, so that is
what gets a name:

```ruby
GraphWeaver::InputProblem           # kind, path, coordinate, value, message, details
GraphWeaver::InputError#problem     # the one that was refused here
GraphWeaver::GraphQLError#input_problem   # nil when the error isn't about input
GraphWeaver::Response#input_problems      # and QueryError#input_problems
```

- `path` — rooted at the **variable**: `["where", "_and", 0, "_not", "species"]`,
  so `$where._and.0._not.species`. This is the coordinate `#field` doesn't give
  today. `nil` when the producer didn't say.
- `coordinate` — the GraphQL [schema coordinate](https://github.com/graphql/graphql-spec/pull/794):
  `"PetFilter.species"`, or `"Mutation.adopt(input:)"` for an argument. `nil`
  when unknown — a graphql-ruby variable-coercion error never names the nested
  input type.

`InputError#field` and `#struct` keep their current meanings; this is additive,
so nothing that reads them breaks. `to_h` gains one key, `"input"`.

## Translating it

```ruby
def render_input_problem(problem)
  I18n.t(
    "graph_weaver.input.#{problem.kind}",
    field: problem.path&.last,
    value: problem.value,
    **problem.details,
    default: problem.message,   # untranslated kinds fall back, never "translation missing"
  )
end

# before the wire
rescue GraphWeaver::InputError => e
  form.errors.add(e.problem.path&.last, render_input_problem(e.problem))

# and after it, the same call
response.input_problems.each { |p| form.errors.add(p.path&.last, render_input_problem(p)) }
```

`default:` is the load-bearing half: `:refused` is untranslatable by definition —
it *is* whatever the message said — so every app needs the fallback, and having
it means an app can translate the four kinds it cares about and leave the rest.

Arrays stay arrays: `details[:members]` is `["CAT", "DOG"]`, so join it where you
know the language — `members: p.details[:members].to_sentence`.

## No locale file ships

graph_weaver would ship the **keys and the data, and no `en.yml`**. Three
reasons, in order:

1. The strings are app-voice, not library-voice. "Species must be one of: cat,
   dog" belongs to whoever owns the form.
2. A shipped default applies by merely adding the gem — behavior that follows
   from the Gemfile rather than from the code in front of you, which is the one
   thing this library refuses to do everywhere else.
3. Owning a user-visible English string means every reword is a breaking change
   for apps that translated around it.

Paste this into your own `config/locales/en.yml` instead:

```yaml
en:
  graph_weaver:
    input:
      type_mismatch: "%{field} must be a %{type}."
      unparseable: "%{field} isn't a valid %{type}."
      not_a_member: "%{field} must be one of: %{members}."
      missing: "%{field} is required."
      unknown: "%{field} isn't a field we recognize."
      out_of_range: "%{field} is out of range."
      invalid_format: "%{field} isn't in the right format."
      refused: "%{field} was rejected."
```

## What the server has to do

For the two kinds nothing can produce on its own, and for any server that isn't
graphql-ruby, the server states it — under one key, so there is one thing to
document and one thing to look for:

```json
"extensions": {
  "code": "BAD_USER_INPUT",
  "input": {
    "kind": "out_of_range",
    "path": ["input", "range", "min"],
    "coordinate": "RangeInput.min",
    "value": 0,
    "min": 1
  }
}
```

`code` is the ecosystem's coarse bucket, so a client that has never heard of
graph_weaver still understands; `input` is the fine one. Only `kind` is required,
and it must come from the table above. In graphql-ruby this rides on a custom
`Validator` raising `GraphQL::ExecutionError.new(msg, extensions:)`, which
survives to the wire verbatim — or, for a scalar, on
`GraphQL::CoercionError.new(msg, extensions:)`, which arrives nested under
`problems[i].extensions`.

**A server that follows none of this degrades, it does not guess.** graph_weaver
reads what graphql-ruby gives for free — a recognized validation `code`, or a
`problems[].explanation` it has a table for, plus `problems[].path` as the path
and `extensions.value` as the value — and everything else becomes `:refused`
carrying the server's message verbatim. A wrong `kind` is worse than no `kind`,
because the app will have translated it into a confident sentence.

## Where translation stops

graph_weaver's own refusals are for developers and stay English, with no keys:
`ValidationError` and the codegen errors (a rake task's output), the schema-drift
hint, `ConfigurationError`, `Testing::*`. Same for `InputProblem#message` — it is
the line in the log and the stack trace; the translated line is the one your app
builds from `kind` and `details`. And a message the *server* wrote arrives in
whatever language the server chose, passed through untouched.
